# Phase 8 Design Investigation — Test Strategy & Production-Readiness Validation

**Status:** design only, per instructions — no implementation code below.
**Scope:** audit the existing unit-test suite across Phases 1–7, identify genuine gaps, formalize the mocked-HTTP testing convention already in use, fold `live-test-reports.md` into the project's permanent validation strategy, and enumerate what still needs live verification before the bridge is "production ready." Nothing here revisits architecture, retry/watermark/fallback decisions, or introduces a new test framework.

**Inputs reviewed:** `docs/implementation-roadmap.md`, `docs/planning.md`, `docs/reverse-engineering-report.md`, `docs/phase-3-auth-design.md`, `docs/phase-4-design.md`, `docs/phase-5-design-temp.md`, `docs/phase-6-design.md`, `docs/phase-7-design.md`, `docs/adr/phase-3-decision-record.md`, `docs/adr/phase-4-decision-record.md`, `docs/adr/phase-5-decision-record.md`, `docs/adr/phase-6-decision-record.md`, `docs/adr/phase-7-decision-record.md`, `live-test-reports.md`, and every shipped `_test.go` file in the tree (`internal/logger`, `internal/util`, `internal/config`, `internal/token` — via `internal/readest`'s tests, `internal/readest`, `internal/bookorbit`, `internal/sync`, `internal/sync/state`, `cmd/bridge`).

**Baseline fact this whole document works from:** Phase 7 is complete, and seven live tests (`live-test-reports.md`) have already exercised the bridge against real Readest and real BookOrbit accounts, covering idempotent re-runs, percentage-delta pushes, both branches of match-check (unmatched and matched), deleted-row handling, daemon mode + SIGINT shutdown, and the delete→re-add "brand-new" property. That is real integration evidence, not a hypothetical — Phase 8's job is to (a) make sure the *unit* layer is complete now that every module is frozen, and (b) turn the *live* evidence that already exists into something durable, while naming exactly what's still unverified.

## 2. Genuine unit-test gaps (the only new unit-test work this document proposes)

Each of these is small, named, and traceable to a specific untested branch — not a general "add more tests" instruction.

| # | Gap | Where | Why it's a real gap | Test level |
|---|---|---|---|---|
| G1 | `internal/token` has no dedicated `token_test.go` | `internal/token/token.go` | It is a standalone package (created specifically to break the `readest`↔`state` import cycle, per the Phase 3 ADR). ## 3. Table-driven utility test strategy — confirmation, not a new plan

The instruction asked specifically about `iso_to_ms`, the dummy-hash filter, percentage calculation, URL normalization, and batching. All five are **already table-driven and already shipped**:

- `ISOToMs` → `util_test.go: TestISOToMs` (6 cases: empty, Zulu, offset, fractional, space-separated no-zone, invalid).
- Dummy-hash filter → not a `util` function; it's `readest.BookRow.IsDummy()`, tested in `models_test.go: TestBookRowPredicates`, and its *engine-level consequence* (dummy rows never reach match-check/watermark) is tested in `engine_test.go: TestRunOnceDummyRowFiltered`. Both levels are covered, which is correct: the pure predicate is a `readest` model-level unit test, and "does the engine actually skip it" is an engine-level unit test — two different behaviors, two different tests, no duplication.
- `Percent` → `util_test.go: TestPercent` (7 cases: half, zero-cur, full, clamp-over-1, rounding, zero-total error, negative-total error, negative-cur error).
- `NormalizeBookOrbitURL` → `util_test.go: TestNormalizeBookOrbitURL` (7 cases covering every normalization rule in the doc comment).
- Batching → `util_test.go: TestBatch` + `TestBatchFunc` (even split, nil, size-0 fallback, full traversal, early-stop).

**Recommendation:** no new table-driven tests are needed for these five; they're a textbook example of the pattern already applied correctly. The only utility-adjacent gaps are G2 (`LowerNormal`) and G3 (`LevelName`) from §2, which are the same table-driven style, just missing a home of their own.

## 4. Mocked-HTTP testing strategy for the Readest and BookOrbit clients — confirmation

Both clients already share one convention, and it should remain the *only* HTTP-mocking approach in this codebase (no `httpmock`, no `gock`, no VCR-cassette library):

- A hand-rolled `stubDoer` implementing `httpclient.Doer`, scripted with an ordered slice of `stubStep{status, body, err, delay}`, recording every request (`requests []*http.Request`, and in the BookOrbit variant, `bodies []string` too) for header/body/path assertions.
- A `delay` field on each step lets a test exercise per-call `context.WithTimeout` deadlines without a real slow server.
- An `alwaysOKDoer` variant (both packages have their own copy) supports the `-race` concurrency tests where request-count assertions aren't the point.
- Fakes for `Authenticator`/`API` (`fakeAuth` in `readest`, `fakeBookOrbit`/`scriptedBookOrbit` in `sync`) are plain hand-written structs satisfying the existing interfaces — no mocking framework, consistent with `docs/implementation-brief.md`'s "avoid unnecessary dependencies."

**Phase 8's job here is purely to confirm this stays the pattern**, and to note the one place it was deliberately *not* used: `cmd/bridge/main_test.go: TestRunOnceFullWiringSurfacesClassifiedError` uses a real `httptest.Server` instead of `stubDoer`, specifically because that test's whole point is proving the *real* `net/http` transport, real JSON encoding, and the full construction chain all agree end-to-end — a `stubDoer` would only prove the internal seam, not the wire format. This was already flagged and justified in `docs/adr/phase-7-decision-record.md`'s "Deviation from the design" section. No change proposed; this is the correct exception to the rule, not a pattern to spread further.

**No new mocked-HTTP work is proposed.** Every classified status code, every malformed-body case, every timeout/cancellation case, and every device-field-stamping case for both clients is already covered per §1's inventory.

### 5.2 Recommended structure for any *future* manual integration test (not new tests being proposed here — a template for §6's remaining items)

Every executed test already follows a consistent, good shape that should be the template going forward:
1. State the purpose and which specific design/ADR claim it targets.
2. Give the operator concrete setup steps (what to change in Readest/BookOrbit).
3. Specify exact expected log lines/state-file fields, including explicit "watch for this regression" negative assertions (e.g., "zero WARN lines mentioning hash absent").
4. Require pasting real output plus the relevant `bridge-state.json` fragment, not just a pass/fail verdict — this is what makes the report independently re-verifiable later.
5. Always include an immediate second run to prove convergence/idempotency, since that's the daemon's core correctness property (Phase 6 §5.4).

No new tooling is needed to keep doing this — it is plain `--once`/`--config`/`BRIDGE_LOG_LEVEL=debug` invocations against real accounts, exactly as documented in the README's "Testing against live accounts" section.

## 6. Remaining scenarios that still require live verification

Ordered roughly by how much they'd change the production-readiness picture if they surfaced a problem.

| # | Scenario | Why it's not yet covered | Priority |

## 7. Decisions requiring approval

Kept short, on purpose — most of this document is confirmation of existing good practice, not a request to change direction.

**A. Add the four small unit tests in §2 (G1–G4): a `token_test.go`, a direct `LowerNormal` test, a direct `LevelName` test, and the two anon-key env-branch cases.**
*Recommend: approve.* Each is a few lines, follows the exact table-driven style already used everywhere else, and closes a named, real gap without touching any already-frozen module's behavior.

**B. Treat G5 (the anon-key base64-decode-failure branch in `config.finalize()`) as optional/deferred.**
*Recommend: defer.* It guards a compile-time constant that can't actually be corrupted at runtime without someone editing the source; a test would need an artificial seam purely to exercise dead-in-practice code. Flagging it here so it isn't silently forgotten, not because it's worth building for.

**C. Accept L2 (bulk→singular-PUT fallback against a real old server), L3 (429 handling), L6 (very large library pull), L7 (Readest hosted-API edge behaviors), and L8 (bulk-progress reporting a hash unmatched) as *documented residual risk* rather than blocking "production ready" on them.**
*Recommend: approve accepting them as documented risk.* All five require either infrastructure the current operator doesn't have (an old BookOrbit version, a 1000+ book library) or a condition that's rare/edge under the bridge's actual documented usage pattern (self-hosted, single operator, 15-minute default poll interval). Manufacturing them artificially would add complexity (fault-injecting proxies, synthetic huge libraries) for scenarios the project's own risk posture already treats as acceptable elsewhere (e.g., `docs/reverse-engineering-report.md` §5 already accepts several of these as inherent, unverifiable-from-source unknowns).

**D. Schedule L1 (SIGTERM) and L4 (live token refresh) as the two remaining live tests to actually run before calling the bridge production-ready**, and update the README's "Known live-server unknowns" list to move the empty-`progress`-string question from *unverified* to *confirmed accepted* (Test 2 already proves this — every push the bridge makes sends `progress: ""`, and Test 2's push succeeded and displayed correctly in BookOrbit).
*Recommend: approve.* L1 is nearly free to redo correctly (just don't block the sending shell on `wait`). L4 needs a >30-minute observation window but requires no code change, just patience and a debug-level log capture. The README correction is a documentation-only fix reflecting evidence that already exists in `live-test-reports.md`.

**E. Formalize a permanent tracking artifact for live-validation status** — e.g. a `docs/live-validation-status.md` (or a dedicated section appended to `live-test-reports.md` itself) that lists every live-validation item originally flagged across Phases 3–6's design docs, its current status (resolved-by-which-test / still-open / accepted-as-residual-risk), so this knowledge doesn't live only inside prose ADR addenda and a chat-style test log.
*Recommend: approve, as a documentation-only artifact — no new automated tooling, no CI integration, consistent with the project's explicit choice throughout Phases 3–7 to rely on documented manual verification for live-server behavior rather than building a live integration-test harness (`docs/phase-7-design.md` §8.4, explicitly reaffirmed in this document's §4 and §5).* This is the mechanism for "how the completed live tests get incorporated into the project's permanent validation strategy" — the seven existing tests, plus L1/L4 once run, would populate it; L2/L3/L6/L7/L8 would be recorded there as accepted risk with the reasoning from §7-C, so a future contributor doesn't have to rediscover why they're not blocking.
